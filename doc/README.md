# Anywayone Blog 产品与技术文档

## 1. 文档目的

本目录用于沉淀 Anywayone Blog 从产品定义到工程落地的核心决策。当前方案以“个人长期维护、内容体验优先、先上线再演进”为原则，面向单作者博客的第一版开发。

## 3. 当前基线决策

| 领域 | 决策 |
| --- | --- |
| 产品形态 | 单作者个人博客，承载文章与摄影作品；前台公开访问，后台仅站长使用 |
| 展示端导航 | 固定为“首页、文章、摄影、关于我”；分类、标签、归档和搜索作为文章发现路径 |
| UI 风格 | 轻动漫编辑风；主站暖白、摄影详情炭黑，橙色仅作小面积品牌与状态强调 |
| 首页结构 | IP 品牌首屏 + 可翻屏的“关于我 / 站点日志”，首页不承载文章和摄影内容流 |
| 关于我职责 | 首页第二屏承载完整个人档案；`/about` 仅承载头像、联系说明和已配置的联系方式 |
| 内容格式 | 文章以 Markdown 为内容源；摄影以有序摄影集为内容源 |
| 仓库结构 | `backend`、`admin`、`web` 三端一体，两个前端的公共代码放入 `packages` |
| 后端 | Python 3.11+ + FastAPI + SQLAlchemy 2.0 + Alembic + Pydantic v2 |
| 工程工具 | 后端使用 `uv`，前端使用 `pnpm workspace`，根目录使用 `Taskfile` 统一命令 |
| 数据库 | PostgreSQL；Redis、独立搜索服务均延后到确有需要时引入 |
| 管理端 | React + Vite + Ant Design |
| 展示端 | Next.js App Router + React，服务端渲染与增量静态再生成并用 |
| API | REST + OpenAPI，统一响应与错误码，生成类型化客户端 |
| 文件存储 | S3 兼容对象存储；本地开发使用 MinIO 或本地适配器 |
| 部署 | Oracle ARM64 + GitHub Actions + Docker Compose + Caddy；PostgreSQL 运行在同机宿主机 |

## 4. 核心原则

1. 内容归作者所有：正文可导出为标准 Markdown，摄影集元数据可导出为 JSON，原图使用可迁移的对象存储。
2. 首屏和阅读优先：前台不依赖登录，不让统计、评论等次要能力阻塞正文。
3. 默认可被发现：SEO、RSS、站点地图、语义化 HTML 和分享卡片属于基础能力。
4. 单体优先：后端采用模块化单体，只有明确的容量或团队边界出现后才拆服务。
5. 渐进增强：缓存、全文搜索、评论、订阅等能力按真实需求添加。
6. 决策可验证：每个里程碑都有验收标准、自动化检查和回滚方式。

## 5. 待产品负责人确认

以下问题不阻塞基础架构，但应在进入对应功能前确认：

- 是否需要开放读者评论；当前路线图将其放在第二阶段。
- 是否需要邮件订阅与文章推送；当前仅在第一版提供 RSS。
- 是否需要中英文双语；当前数据模型预留但首版按单语言实现。
- 是否公开文章浏览量；当前采集基础数据但默认不在前台强调展示。
- 是否需要独立的“作品/项目”内容类型；当前先用自定义页面承载。

## 6. 文档维护规则

- 产品范围变化时，先更新 PRD，再同步产品设计、数据模型和路线图。
- 技术选型变化时，在技术架构文档记录原因、替代方案和迁移影响。
- API 与数据模型以代码和自动生成的 OpenAPI 为最终事实来源，本文档描述稳定边界。
- 完成一个里程碑后，更新路线图状态并补充实际偏差。
