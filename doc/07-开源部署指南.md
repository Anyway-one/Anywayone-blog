# Anywayone Blog 开源自托管部署指南

## 1. 文档边界

本文档面向 Fork 或下载 Anywayone Blog 后自行部署的维护者，只描述可公开复用的部署流程。

本文档不会记录 Anywayone 官方站点的服务器 IP、SSH 密钥路径、证书邮箱、数据库密码、生产账号、备份位置或事故记录。维护者自己的环境信息应放在仓库外，或放入已被 Git 忽略的 `doc/private/`。

仓库提供的是一套单机自托管参考实现：

- GitHub Actions 执行检查并构建 Docker 镜像。
- GHCR 保存 Web、Admin 和 Backend 镜像。
- Docker Compose 在服务器运行三个应用和 Caddy。
- Caddy 负责 HTTPS、根域名跳转和反向代理。
- PostgreSQL 安装在宿主机，不包含在 Compose 中。
- Alembic 在应用更新前自动升级数据库结构。

这不是一键部署模板。当前工作流、镜像名称、域名和健康检查仍包含 Anywayone 项目的默认值，Fork 后必须先完成第 3 节的定制。

## 2. 参考拓扑

```text
Internet
   |
DNS / CDN
   |
Server :80/:443
   |
Caddy
   |-- www.example.com   -> web:3000
   |-- admin.example.com -> admin:8080
   `-- api.example.com   -> backend:8000
                                  |
                                  `-> host PostgreSQL:5432
```

只向公网开放 `80` 和 `443`。SSH `22` 建议限制到可信公网 IP。`3000`、`8080`、`8000` 和 `5432` 不应在云防火墙中公开。

## 3. Fork 后必须修改的项目绑定

在首次构建前全局搜索以下默认值：

```bash
rg -n "Anyway-one|anywayone\.com|anywayone-|/opt/anywayone|172\.30\.0\.0/24" \
  .github deploy web/Dockerfile admin/Dockerfile
```

至少检查这些位置：

| 文件 | 默认绑定 | Fork 后处理 |
| --- | --- | --- |
| `.github/workflows/deploy.yml` | 原仓库名称判断 | 改为自己的 `owner/repository`，否则 Fork 不会构建和部署 |
| `.github/workflows/deploy.yml` | GHCR 命名空间和镜像名 | 改为自己的 GitHub owner 与镜像名 |
| `.github/workflows/deploy.yml` | Web、Admin、API 公开地址 | 改为自己的正式域名 |
| `.github/workflows/deploy.yml` | `linux/arm64` | x86 服务器改为 `linux/amd64`；多架构可填写两者 |
| `deploy/Caddyfile` | 四个 Anywayone 域名 | 改为根域名、Web、Admin 和 API 域名 |
| `deploy/scripts/deploy.sh` | 三个健康检查地址 | 改为自己的公开 HTTPS 地址 |
| `deploy/compose.yml` | GHCR 镜像名和 Docker 子网 | 与工作流、PostgreSQL 规则保持一致 |
| `web/Dockerfile` | 默认站点和 API 地址 | 改为自己的构建默认值，或始终由工作流覆盖 |
| `admin/Dockerfile` | 默认 Web 和 API 地址 | 改为自己的构建默认值，或始终由工作流覆盖 |
| `/opt/anywayone` | 服务器部署目录 | 保留即可；若修改，需同步工作流和部署脚本 |

完成修改后执行：

```bash
git diff --check
bash -n deploy/scripts/deploy.sh
```

本机安装 Docker 时还应执行：

```bash
cp deploy/.env.example deploy/.env
cp deploy/backend.env.example deploy/backend.env
docker compose --file deploy/compose.yml config --quiet
docker run --rm \
  --env ACME_EMAIL=admin@example.com \
  --volume "${PWD}/deploy/Caddyfile:/etc/caddy/Caddyfile:ro" \
  caddy:2-alpine \
  caddy validate --config /etc/caddy/Caddyfile
```

官方 Caddy 镜像需要显式执行 `caddy validate`，不能只传递 `validate`。

## 4. 服务器要求

建议的首个生产环境：

- Ubuntu 24.04 LTS 或同等级 Linux 发行版。
- 2 核 CPU、4GB 以上内存和 40GB 以上磁盘。
- ARM64 或 AMD64，必须与工作流的 `platforms` 一致。
- Docker Engine、Docker Compose v2、PostgreSQL 16+。
- 可从服务器访问 GHCR、Let's Encrypt 和 GitHub。
- 服务器时间同步正常。

部署前还需要准备：

- 一个可管理 DNS 的域名。
- 一个可接收 ACME 通知的邮箱。
- 一个可推送 GHCR 镜像并配置 Environment 的 GitHub 仓库。
- 服务器的 `sudo` 权限和密钥 SSH 访问。

在 Ubuntu 上建议使用 Docker 官方软件源：

```bash
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

. /etc/os-release
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu ${VERSION_CODENAME} stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list >/dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
```

验证安装结果：

```bash
uname -m
docker version
docker compose version
sudo docker run --rm hello-world
```

如果 `apt` 被占用，应先确认 `apt-daily` 或 `unattended-upgrades` 是否仍在正常工作。不要删除 `/var/lib/apt/` 或 `/var/lib/dpkg/` 下的锁文件。

## 5. DNS 与防火墙

### 5.1 DNS

首次签发证书前，将 DNS/CDN 代理保持为 `DNS only`：

| 类型 | 名称 | 目标 |
| --- | --- | --- |
| A | `@` | 服务器公网 IPv4 |
| CNAME | `www` | 根域名 |
| CNAME | `admin` | 根域名 |
| CNAME | `api` | 根域名 |

从公共解析器确认真实结果，避免本机代理软件的 Fake-IP 造成误判：

```bash
dig @1.1.1.1 +short A example.com
dig @1.1.1.1 +short A www.example.com
dig @1.1.1.1 +short A admin.example.com
dig @1.1.1.1 +short A api.example.com
dig @1.1.1.1 +short AAAA example.com
```

没有配置 IPv6 服务时，不要保留指向错误地址的 AAAA 记录。

### 5.2 两层防火墙

云厂商安全组和服务器本机的 iptables/nftables 都必须检查。云安全组开放端口不代表操作系统已经放行。

建议的公网规则：

| 来源 | 协议 | 端口 | 用途 |
| --- | --- | --- | --- |
| 可信公网 IP `/32` | TCP | 22 | SSH |
| `0.0.0.0/0` | TCP | 80 | HTTP 跳转与 ACME |
| `0.0.0.0/0` | TCP | 443 | HTTPS |

检查服务器规则：

```bash
sudo iptables -S INPUT
sudo ss -lntp
```

若 INPUT 链末尾存在统一 REJECT/DROP，必须在它之前放行 `80` 和 `443`，并使用服务器已有的持久化机制保存。不要盲目复制规则序号，先查看当前链的顺序。

PostgreSQL 的 `5432` 只允许应用 Docker 子网访问，不能向 `0.0.0.0/0` 开放。Docker 自动生成的 `br-xxxxxxxxxxxx` 接口名可能在网络重建后变化，防火墙规则不应只依赖这个临时接口名；至少同时限制源网段和目标端口。

## 6. 部署用户

GitHub Actions 不应使用日常管理账号或个人 SSH 私钥。创建独立部署用户：

```bash
sudo adduser --disabled-password --gecos "" blogdeploy
sudo usermod -aG docker blogdeploy
sudo install -d -m 700 -o blogdeploy -g blogdeploy /home/blogdeploy/.ssh
sudo install -d -m 750 -o blogdeploy -g blogdeploy /opt/anywayone
```

Docker 组具有接近 root 的权限。该用户只能用于部署，并应使用一把专用 SSH 密钥。

在本机生成并安装部署公钥：

```bash
ssh-keygen -t ed25519 -a 100 -C "blog-github-actions" -f ~/.ssh/blog_github_actions
ssh-copy-id -i ~/.ssh/blog_github_actions.pub blogdeploy@SERVER_IP
ssh -i ~/.ssh/blog_github_actions blogdeploy@SERVER_IP
```

不要将私钥复制到仓库或服务器项目目录。

## 7. PostgreSQL

在宿主机安装 PostgreSQL，并使用专用低权限角色：

```bash
sudo apt install -y postgresql postgresql-contrib
sudo systemctl enable --now postgresql
sudo -u postgres createuser --pwprompt blog_app
sudo -u postgres createdb --owner=blog_app blog_db
```

允许固定 Docker 子网连接：

```bash
sudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*';"
sudo -u postgres psql -tAc "SHOW hba_file;"
```

在实际 `pg_hba.conf` 末尾加入：

```text
host    blog_db    blog_app    172.30.0.0/24    scram-sha-256
```

然后重启 PostgreSQL：

```bash
sudo systemctl restart postgresql
sudo ss -lntp | grep 5432
```

`listen_addresses = '*'` 只表示进程监听网卡，仍必须由云防火墙、本机防火墙和 `pg_hba.conf` 共同限制访问。

## 8. 生产环境文件

在服务器创建两个仅部署用户可读的文件：

```bash
sudo install -m 600 -o blogdeploy -g blogdeploy /dev/null /opt/anywayone/.env
sudo install -m 600 -o blogdeploy -g blogdeploy /dev/null /opt/anywayone/backend.env
openssl rand -hex 32
```

`/opt/anywayone/.env`：

```dotenv
ACME_EMAIL=admin@example.com
IMAGE_TAG=latest
```

`/opt/anywayone/backend.env`：

```dotenv
APP_ENV=production
DATABASE_HOST=host.docker.internal
DATABASE_PORT=5432
DATABASE_NAME=blog_db
DATABASE_USER=blog_app
DATABASE_PASSWORD=replace-with-a-strong-password
DATABASE_SSL_MODE=disable
DATABASE_POOL_SIZE=5
DATABASE_MAX_OVERFLOW=5
SECRET_KEY=replace-with-at-least-32-random-characters
ACCESS_TOKEN_EXPIRE_MINUTES=15
REFRESH_TOKEN_EXPIRE_DAYS=30
CORS_ORIGINS=https://www.example.com,https://admin.example.com
COOKIE_SECURE=true
```

同机私网连接可以使用 `DATABASE_SSL_MODE=disable`，前提是 `5432` 没有暴露到公网。跨主机数据库应启用并验证 TLS。

生产数据库密码和 Backend `SECRET_KEY` 只保存在服务器，不需要写入 GitHub Secrets。

## 9. GitHub Environment

创建名为 `production` 的 GitHub Environment，并配置：

| Secret | 内容 |
| --- | --- |
| `DEPLOY_HOST` | 服务器公网 IP 或主机名 |
| `DEPLOY_PORT` | SSH 端口，通常为 `22` |
| `DEPLOY_USER` | 专用部署用户 |
| `DEPLOY_SSH_KEY` | 专用部署私钥全文 |
| `DEPLOY_KNOWN_HOSTS` | 已人工验证的 SSH 主机密钥记录 |

获取主机记录前，应先通过服务器控制台核对主机公钥指纹：

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
ssh-keyscan -H -p 22 SERVER_IP
```

不要关闭 `StrictHostKeyChecking` 来绕过主机校验。

## 10. 首次部署

生产 job 由仓库变量 `PRODUCTION_ENABLED=true` 控制。推荐顺序：

1. 暂不创建 `PRODUCTION_ENABLED`。
2. 推送定制后的代码，让工作流只执行 CI 和镜像构建。
3. 确认三个 GHCR 镜像存在，并允许服务器读取。公开仓库可以使用 Public 包；私有包需要额外配置 GHCR 登录凭证。
4. 确认 DNS、服务器环境文件、PostgreSQL 和防火墙已经就绪。
5. 创建仓库变量 `PRODUCTION_ENABLED=true`。
6. 手动运行 `Deploy production`，或再次推送 `main`。

流水线会执行：

1. Web、Admin、Backend 和部署配置检查。
2. 构建目标架构镜像并推送到 GHCR。
3. 使用 Git commit SHA 生成不可变镜像标签。
4. 上传 Compose、Caddy 和部署脚本。
5. 执行 `alembic upgrade head`。
6. 更新容器并等待健康状态。
7. 检查三个公开 HTTPS 地址。
8. 成功后记录 `.deployed-image-tag`；失败时尝试恢复上一镜像标签。

首次部署没有上一版本可恢复，因此上线前的 CI、镜像可读性和环境检查尤其重要。

当 GHCR 包保持 Private 时，当前 Compose 部署需要先让服务器登录 GHCR。为部署用户创建仅有 `read:packages` 权限的 token，通过标准输入登录：

```bash
printf '%s' "$GHCR_READ_TOKEN" \
  | docker login ghcr.io --username GITHUB_USERNAME --password-stdin
chmod 600 ~/.docker/config.json
```

`GITHUB_TOKEN` 只在 Actions 任务内有效，不能直接作为服务器的长期拉取凭证。上述 token 应由密码管理器管理，不得写入仓库文件。

## 11. HTTPS 与 CDN

首次证书签发期间保持 DNS Only。确认以下地址均能以可信证书访问后，再开启 CDN 代理：

- `https://www.example.com`
- `https://admin.example.com/login`
- `https://api.example.com/health/ready`

Cloudflare 应使用：

```text
SSL/TLS encryption mode: Full (strict)
```

不要使用 `Flexible`。开启代理后再次验证三个地址，并确认 API 的 CORS 来源仍与浏览器实际域名一致。

Caddyfile 当前固定使用 Let's Encrypt 正式端点。若日志出现 TLS internal error，先检查 Caddy 日志中的 ACME 结果，不要使用 `curl -k` 掩盖证书问题。

## 12. 创建首个管理员

Alembic 只创建表，不创建业务管理员。首次部署成功后，在服务器交互式执行：

```bash
cd /opt/anywayone
docker compose exec backend python -m app.cli create-admin
```

命令会询问邮箱、显示名称和至少 12 位密码。密码不会回显，也不应作为命令行参数、聊天消息或 GitHub Secret 传递。

## 13. 日常运维

状态、日志和迁移版本：

```bash
cd /opt/anywayone
docker compose ps
docker compose logs --tail=200 caddy
docker compose logs --tail=200 backend
docker compose exec -T backend alembic current
cat .deployed-image-tag
```

手动执行迁移：

```bash
docker compose run --rm --no-deps backend alembic upgrade head
```

使用已存在的不可变镜像标签回退应用：

```bash
IMAGE_TAG=sha-FULL_GIT_SHA docker compose up -d --remove-orphans --wait
```

应用回退不会自动回退数据库。生产迁移必须保持向后兼容，破坏性变更应采用“扩展、迁移数据、收缩”的多版本流程。

## 14. 备份与恢复

自动部署不等于数据库备份。上线前至少建立：

- PostgreSQL 每日逻辑备份。
- 备份文件加密和异地保存。
- 明确的保留周期与容量告警。
- 每月至少一次恢复演练。
- Caddy 数据卷以及已启用对象存储的恢复策略。

先确定可接受的数据丢失时间（RPO）和服务恢复时间（RTO），再决定备份频率。可以使用 PostgreSQL 自定义格式生成可校验的逻辑备份：

```bash
sudo install -d -m 700 -o postgres -g postgres /var/backups/postgresql
sudo -u postgres pg_dump --format=custom \
  --file=/var/backups/postgresql/blog_db.dump blog_db
sudo -u postgres pg_restore --list \
  /var/backups/postgresql/blog_db.dump >/dev/null
```

备份作业成功不代表数据一定可恢复。定期恢复到临时数据库并执行业务校验：

```bash
sudo -u postgres createdb --owner=blog_app blog_restore_test
sudo -u postgres pg_restore --exit-on-error --no-owner \
  --role=blog_app --dbname=blog_restore_test \
  /var/backups/postgresql/blog_db.dump
```

验证表、记录数和关键查询后，再删除这个临时数据库。备份文件名、实际路径、凭证和异地存储位置应由私有运维系统管理，不要写进开源仓库。

## 15. 监控与更新

至少对以下信号设置告警：

- `https://api.example.com/health/ready` 非 `200`。
- Web 和 Admin 入口无法访问或证书即将过期。
- 宿主机磁盘、内存或负载持续超过阈值。
- Docker 容器反复重启或处于 `unhealthy` 状态。
- 备份作业失败、备份大小异常或长期未完成恢复演练。

Compose 已对容器日志设置大小和保留数限制，但这不是持久化日志系统。每月安排操作系统安全更新，并通过测试环境或可回退的时间窗口更新 Docker、PostgreSQL 和容器基础镜像。

## 16. 常见故障

### 容器连接 PostgreSQL 返回 `No route to host`

依次检查：

1. PostgreSQL 是否监听宿主机地址。
2. `host.docker.internal` 在容器内解析到哪个地址。
3. INPUT 链是否在允许规则之前 REJECT/DROP。
4. Docker 子网是否与 `pg_hba.conf` 一致。
5. Docker 网络重建后网桥接口名是否变化。

### `CORS_ORIGINS` 启动解析失败

当前后端支持逗号分隔格式。部署旧镜像时若看到 JSON 解析错误，应升级到包含 `NoDecode` 配置修复的版本，不要把生产值临时改成不可维护的格式后遗忘。

### Caddy 返回 TLS alert internal error

查看：

```bash
docker compose logs --tail=300 caddy
```

重点确认 DNS 是否直达源站、80/443 是否在两层防火墙放行、ACME challenge 是否成功以及证书是否从正式 CA 下载完成。

### 本地 `dig` 返回 `198.18.0.0/15`

这通常是代理软件的 Fake-IP。使用 `dig @1.1.1.1` 查询公共 DNS，不要把 Fake-IP 当作真实解析结果。

## 17. 安全检查清单

- 私钥、数据库密码、`SECRET_KEY` 和真实 `.env` 未进入 Git。
- GitHub Actions 使用独立部署密钥和 `production` Environment。
- SSH 仅允许密钥登录，并尽量限制来源 IP。
- 只有 80/443 对公网开放，5432 未公开。
- Cloudflare 使用 Full (strict)。
- GHCR 私有包没有被匿名拉取依赖阻断。
- 管理员密码至少 12 位且未通过命令行参数传递。
- 数据库备份经过实际恢复验证。
- 系统和容器基础镜像有定期更新计划。

## 18. 私有运维记录

项目维护者可以在本地创建：

```text
doc/private/
```

该目录已被 `.gitignore` 忽略，适合记录真实服务器清单、当前镜像标签、Cloudflare 状态、备份位置和处理过程。即使目录被忽略，也不要在其中长期保存私钥正文或明文密码；密码应交给密码管理器或服务器权限受控的环境文件。
