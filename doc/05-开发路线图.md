# Anywayone Blog 开发路线图

## 1. 实施原则

- 先贯通一条可上线的内容链路，再增加横向功能。
- 每个里程碑产出可运行、可演示、可回滚的版本。
- 数据库迁移、权限和安全渲染从第一天进入工程，不作为上线前补丁。
- 个人项目不建议按“前端全部完成后等后端”的方式开发；应按纵向功能切片推进。
- 以下周期以一名有相关经验的全职开发者为参考，实际应按可投入时间调整。

## 2. 里程碑总览

| 阶段 | 参考周期 | 目标产物 | 可演示结果 |
| --- | --- | --- | --- |
| M0 产品与工程基线 | 3-5 天 | Python/前端单仓、环境、CI、设计 token、ADR | 三端可启动并通过 CI |
| M1 内容最小闭环 | 2 周 | 登录、文章 CRUD、Markdown、公开详情 | 写一篇文章并公开阅读 |
| M2 可发布的 MVP | 2-3 周 | 分类标签、媒体、摄影集、定时发布、首页档案、SEO | 文章与摄影作品均可正式发布 |
| M3 发现与可靠性 | 1-2 周 | 搜索、归档、RSS、版本、备份、监控 | 可发现、可恢复、可运维 |
| M4 上线与稳定 | 1 周 | 部署、安全/性能/兼容验收 | 生产环境稳定运行 |
| M5 运营增强 | 按需 | 数据概览、自定义页面、评论或订阅验证 | 根据真实使用反馈迭代 |

保守估算 MVP 上线需要约 7-9 周全职投入。摄影集增加了批量媒体、排序和大图体验，不能只按一个普通列表页估算。若是业余开发，应保留同等工作量，不要用压缩测试和备份来换取表面进度。

## 3. M0：产品与工程基线

### 3.1 范围

- 确认 PRD 中的 MVP 边界和待确认项。
- 建立 Python 3.11+ / FastAPI 后端、pnpm workspace 前端和三端基础工程。
- 后端使用 `uv` 与 `pyproject.toml`，前端使用 `pnpm`，根目录用 `Taskfile` 统一命令。
- 提供 PostgreSQL 与对象存储的本地开发环境。
- 配置 Ruff、Pyright、前端 TypeScript lint/format 以及 commit/branch 基本规范。
- 配置 CI：类型检查、测试、构建、依赖扫描。
- 建立环境配置模板与启动时校验，区分 local/test/production。
- 确立基础设计 token、前台排版样式和管理端主题。
- 建立架构决策记录（ADR）目录，记录重要技术选择。

### 3.2 验收

- 新开发者按 README 在 15 分钟内启动三端和依赖服务。
- `task lint`、`task test`、`task build` 可从仓库根目录检查 Python 后端和两个前端。
- Backend 可连数据库并返回健康检查。
- Web 和 Admin 可通过类型化客户端调用一个示例接口。
- 提交中不包含密钥、开发者本机路径或 IDE 必需配置。

## 4. M1：内容最小闭环

### 4.1 后端

- SQLAlchemy 用户、会话、文章和版本模型及 Alembic 初始迁移。
- 管理员初始化方式、登录、刷新、退出和会话吊销。
- 文章新建、查询、保存、发布、撤回接口。
- 乐观锁 revision 和冲突响应。
- Python Markdown 渲染、安全清洗、目录和阅读时长。
- FastAPI 公开文章详情 API 和 OpenAPI 生成的 TypeScript 客户端。
- 审计日志和发布 Outbox 最小实现。

### 4.2 管理端

- 登录页和受保护路由。
- 文章列表基本状态筛选。
- CodeMirror Markdown 编辑器、预览、自动保存和保存状态。
- 标题、Slug、摘要编辑。
- 发布前检查、发布确认和成功反馈。
- 网络失败本地保护与离开页面提醒。

### 4.3 展示端

- 全局导航、主题、基础 SEO 默认值。
- 文章详情页、目录、代码高亮/复制、响应式图片基础。
- 404 和错误页。
- 公开页面缓存和发布后失效的最小链路。

### 4.4 测试与验收

- 接口测试覆盖未登录、非法数据、版本冲突、发布与撤回。
- 恶意 Markdown 样本不能执行脚本或危险属性。
- Playwright 完成“登录 -> 新建 -> 自动保存 -> 发布 -> 前台阅读”。
- 360px 和桌面视口文章页无布局溢出。
- 后端重启、页面刷新和短暂断网不造成已确认保存的内容丢失。

## 5. M2：可发布的 MVP

### 5.1 内容组织

- 分类、标签数据模型及后台管理。
- 文章分类/标签选择、置顶和可见性。
- 文章列表、分类页和标签页；首页保持品牌首屏与个人档案结构，不承载内容流。
- Slug 修改与永久重定向。

### 5.2 媒体

- 对象存储适配和预签名上传。
- 编辑器拖拽/粘贴图片。
- 媒体库、替代文本、引用关系和删除保护。
- 派生尺寸、WebP/AVIF 策略和异常重试。

### 5.3 摄影

- 摄影集与有序照片的 SQLAlchemy 模型、Alembic 迁移和 FastAPI 接口。
- 后台摄影集列表、创建、批量选图、拖拽/键盘排序、预览、发布和撤回。
- 展示端 `/photography` 列表、`/photography/:slug` 详情和可访问的大图查看。
- 摄影页精选策展、摄影 SEO、sitemap 与缓存失效；摄影集不进入首页。
- 联系页面 `/about` 和后台联系方式配置；完整个人档案配置供首页第二屏使用。

### 5.4 发布能力

- 定时发布扫描、幂等发布和失败提醒。
- SEO 字段、Open Graph、Twitter/X card、Article JSON-LD。
- canonical、robots 和 noindex 规则。
- 首页/文章/摄影/关于我/分类/标签的精确缓存失效。

### 5.5 测试与验收

- 定时发布并发执行只发布一次，失败可重试。
- 已发布文章改 Slug 后旧链接返回 308 且无重定向链。
- 未列出内容不进入列表、搜索前置数据和 sitemap。
- 被引用媒体无法误删；失败上传能被清理。
- 摄影集至少包含一张 READY 图片才能发布，封面属于当前摄影集，排序保存后稳定。
- 摄影大图支持键盘、触控和焦点恢复，移动端不下载不必要的整组原图。
- Lighthouse 在生产构建下达到：Performance ≥ 90、Accessibility ≥ 95、Best Practices ≥ 95、SEO ≥ 95。分数是守门指标，仍需检查真实 Web Vitals。

## 6. M3：发现与可靠性

### 6.1 内容发现

- 归档页与分页。
- PostgreSQL 全文/模糊搜索，中文数据集验证相关性。
- RSS、sitemap 和 robots 输出。
- 上一篇/下一篇及轻量相关文章。

### 6.2 数据可靠性

- 版本列表、差异查看和恢复。
- Markdown + JSON 内容导出。
- PostgreSQL 与对象存储自动备份。
- 在隔离环境执行一次完整恢复演练并记录耗时/问题。
- 回收站、失败上传、过期会话和 Outbox 清理任务。

### 6.3 可观测性

- JSON 日志、requestId、前后端错误追踪。
- 请求、数据库、Worker 和备份最小指标。
- 站点不可用、发布失败、备份失败、磁盘空间告警。
- 工作台展示最近草稿和需要处理的系统提醒。

### 6.4 测试与验收

- 新发布、修改、撤回均能正确同步搜索、RSS、sitemap 和缓存。
- 搜索结果不泄漏草稿、定时或撤回内容。
- 可在全新环境从备份恢复文章、摄影集、分类、标签、设置和媒体引用。
- Outbox/定时任务模拟中断后可继续消费，且结果不重复。
- 日志中不出现 Cookie、密码、令牌和完整正文。

## 7. M4：上线与稳定

### 7.1 上线准备

- 准备 production Docker Compose/部署清单和反向代理。
- 配置域名、HTTPS、CDN/对象存储域名和安全响应头。
- 使用独立生产密钥和最小权限数据库/存储账号。
- 配置备份、错误追踪、监控和告警接收渠道。
- 迁移现有文章或准备首批正式内容。
- 制定升级、回滚、恢复和管理员锁定处理手册。

### 7.2 上线检查表

功能：

- 登录、自动保存、预览、立即/定时发布、撤回均通过。
- 首页、文章、摄影、关于我四项一级导航在无登录状态可用；分类、标签、归档和搜索可从文章路径进入。
- RSS、sitemap、canonical、分享卡片和 404 正确。
- 备份与恢复已真实验证。

安全：

- 生产无默认账号/密码，初始化入口已关闭。
- Cookie、安全响应头、CSRF、限流和上传校验已验证。
- 管理 API 不被搜索引擎索引，数据库/内部端口不暴露公网。
- 依赖和镜像无未接受的高危漏洞。

体验：

- 移动/桌面核心页面通过视觉回归。
- 键盘操作、焦点、对比度和语义标题通过检查。
- 慢网、图片失败、API 失败和空数据状态可理解。
- 长标题、长代码和宽表格不破坏布局。

运维：

- 健康检查和告警已模拟触发。
- 日志可通过 requestId 串联一次请求。
- 磁盘、数据库连接、任务积压和备份时间可观测。
- 应用镜像和上一个稳定版本均可获取。

### 7.3 上线后 72 小时

- 重点观察 5xx、Web Vitals、数据库慢查询、缓存命中、发布任务和存储失败。
- 每日验证备份状态和 sitemap 抓取情况。
- 只修复阻塞问题和明显回归，避免立刻进行大规模功能改造。
- 记录实际发布时长、写作摩擦和读者反馈，作为 v1.1 输入。

## 8. M5：运营增强（按证据启动）

候选项按触发信号排序：

| 信号 | 候选能力 | 启动前验证 |
| --- | --- | --- |
| 作者需要发布关于我之外的固定内容 | 独立页面与页脚入口 | 使用频率和字段是否稳定 |
| 无法了解哪些旧内容仍有价值 | 隐私友好的基础统计 | 是否可由现有分析服务满足 |
| 读者有明确互动诉求 | Webmention/评论 | 审核和反垃圾维护成本 |
| RSS 覆盖不足且读者愿意订阅 | 邮件订阅 | 合规、退订、发信信誉和费用 |
| 文章形成连续主题 | 系列/专题 | 与分类标签的边界 |
| 中文搜索相关性不足 | 独立搜索服务 | 已有查询样本和性能数据 |

## 9. 纵向开发顺序

不要把三端拆成三个长期并行且最后才集成的项目。每个功能按以下顺序形成闭环：

1. 明确用户场景与验收标准。
2. 设计数据库迁移、领域规则和 API 契约。
3. 完成后端用例与接口测试。
4. 从 FastAPI OpenAPI 生成客户端，完成管理端写流程。
5. 完成展示端读流程和 SEO。
6. 补齐端到端、可观测性和失败状态。
7. 在预发布环境演示后合并。

首批纵向切片建议：

```text
健康检查 -> 登录会话 -> 草稿保存 -> 文章发布 -> 公开详情
-> 文章列表 -> 分类标签 -> 媒体 -> 摄影集 -> 关于我 -> 定时发布 -> 搜索与 RSS
```

## 10. 工作拆分建议

每个任务应小到 0.5-2 天内可评审，示例：

- “实现文章系统”过大，应拆为 schema、创建草稿、保存与 revision、发布用例、公开 DTO、缓存失效等。
- “完成编辑器”过大，应拆为基础编辑、预览、自动保存、图片粘贴、冲突处理、发布设置等。
- “做 SEO”过大，应拆为元信息、canonical、JSON-LD、sitemap、RSS、robots 和验证工具。

每个 Pull Request 应包含：需求/问题、实现范围、测试证据、数据库或配置影响、截图（涉及 UI 时）、回滚注意事项。

## 11. Definition of Done

一个功能只有同时满足以下条件才算完成：

- 验收场景通过，异常和空状态已处理。
- 权限、输入校验和审计符合功能风险。
- 单元/集成/端到端测试按风险补齐。
- API、迁移、环境变量和运维影响有文档。
- 前台功能完成响应式、可访问性和 SEO 检查。
- 日志和指标足以定位生产问题，且不泄漏敏感信息。
- CI 全部通过，预发布环境完成冒烟验证。
- 存在明确的回滚或降级方式。

## 12. 主要风险与应对

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| MVP 不断加功能 | 每周新增范围多于完成范围 | 以 P0 验收闭环为冻结线，P1/P2 进后续池 |
| 编辑器消耗过多时间 | 自研大量富文本行为 | 坚持 Markdown 源，复用 CodeMirror 插件，延后块编辑器 |
| 三端契约漂移 | 重复手写类型、联调频繁返工 | OpenAPI 生成客户端 + CI 差异检查 |
| 中文搜索效果差 | 标题能搜、正文相关性混乱 | 建立真实查询集，先 trigram，达不到标准再换引擎 |
| 图片成本和性能失控 | 原图直出、CLS 高、存储增长快 | 派生图、响应式尺寸、压缩策略和存储指标 |
| 自动保存覆盖内容 | 多标签页编辑或网络恢复后丢稿 | revision 乐观锁、本地草稿、冲突对比 |
| 定时发布不可靠 | 重复发布、延迟、失败无提示 | 行锁、幂等用例、Outbox、指标和告警 |
| 备份不可恢复 | 只有备份文件无演练 | M3 前完成隔离环境恢复，定期复测 |
| 个人运维负担过高 | 更新/监控耗时超过写作 | 优先托管数据库/对象存储，减少有状态组件 |
| UI 过度设计 | 首页装饰多、正文与编辑体验滞后 | 先完成真实长文与移动端内容压力测试 |

## 13. 首批待办清单

建议按以下顺序进入实际开发：

1. 评审并确认 `doc/01-PRD.md` 的 MVP 和待确认项。
2. 清理仓库中的示例文件，确定 Python 3.11+、uv、Node.js、pnpm 版本和许可证。
3. 初始化 FastAPI/uv 后端、pnpm workspace 前端、Taskfile 与公共配置包。
4. 建立本地 PostgreSQL/对象存储和配置模板。
5. 实现健康检查、CI 与第一条端到端连通测试。
6. 编写用户、会话、文章、版本、审计、Outbox 的首批 SQLAlchemy 模型与 Alembic 迁移。
7. 从“管理员登录”和“草稿保存”两个纵向切片开始实现。
